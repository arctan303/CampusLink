# MWAN-02：四路均衡与故障切换

目标：将已联网的 wan1–wan4 接入 mwan3-nft，给 LAN 新连接提供等权均衡、单路故障剔除与恢复。

依据：REQ-003 / AC-007；用户在 MWAN-01 预检后明确授权“可以开始研究和设置”。四路等权初始方案已获得本次实施授权。

范围：mwan3 与必要的流量卸载配置；保留原 WAN、四路网络/认证绑定、LAN 和无线管理配置。校园网插件由另一处维护，不改其代码或凭据。代理/VNT 留待后续，不刷机。

规模与风险：短产品任务，R1。策略错误可能影响 LAN 上网，但影响可由配置备份、自动恢复和原管理路径界定与回滚；不修改 LAN 地址、设备或访问权限。

预期行为：wan1–wan4 同级、等权；LAN IPv4 连接分散到四路，掉线线路退出均衡并在恢复后重新加入；路由器认证请求仍绑定其原出口；原 WAN 保留主表默认路由与 DNS。关闭流量卸载用于本次稳定接入，后续如需加速另行验证。

依赖：复核 MWAN-01 所示四路租约、101–104 源路由表、当前 CampusLink 出口绑定及 mwan3-nft 3.6.12-r4 的实际行为。

实施：完成。验证：下述分流、接口故障及恢复通过，认证失效场景仍有已知缺口。独立审查：R1 不适用。发布：已在授权路由器启用并回读，开机启动已启用；未为验证重启设备。

验证与证据：四路健康跟踪、成员表默认路由、NAT/标记及 WLAN 客户端实际多连接分布；单路失效剔除与恢复；逐路指定出口 HTTP 204、CampusLink 状态、管理页面及 fw4 检查。测试套接字绑定现有 WLAN 地址与接口，不改变宿主机路由、代理或 DNS 设置。

恢复：部署前保存当前 mwan3/firewall/network 和服务启用状态；确认测试通过后已用 `confirmed` 标记解除定时恢复，恢复保护没有触发。手动回退仍可用，详见下文。

## 实际配置（2026-10-08 16:51–17:10，Asia/Singapore）

- mwan3-nft 3.6.12-r4 使用四个 IPv4 成员，metric=1、weight=1。成员表为 1–4，通过 globals.rt_table_lookup 读取现有 101–104 源路由表。
- LAN 规则同时匹配 `iifname br-lan` 与 `192.168.0.0/24`，按连接分流，sticky=0；路由器自身的认证请求不会匹配这条规则。四路均失败时 `last_resort=default` 回到原物理 WAN 主表，单路策略为 unreachable。
- ping 跟踪目标为 223.5.5.5、119.29.29.29，至少一个成功即可；正常间隔 5 秒，失败/恢复间隔 3 秒，连续 3 次改变状态，超时 2 秒。启动状态 offline，通过跟踪才纳入策略。
- 原物理 WAN 主表默认路由、DNS、LAN/无线及 `/etc/config/network` 保留。network 前后 SHA256 相同：`420128977d1961448c782b5fd4c8f2dac2e85575b42774249a90a1d1e6e0f1ea`。
- 防火墙文件自查确认只有软件/硬件卸载值从 1 改为 0，运行规则不再有 flowtable。没有修改校园网插件代码、账号或配置，部署时插件版本为 0.1.0。
- 配置已保存，network/firewall/mwan3 的 UCI 变更缓冲均为空，`/etc/init.d/mwan3 enabled` 返回 0。

## 行为证据

Windows 客户端使用既有 WLAN（接口 8，192.168.0.139），显式绑定套接字出口，向两个路由器当时解析出的华为 204 服务 IP 建立独立连接。用持有 HTTP 套接字期间的 `/proc/net/nf_conntrack` 做只读捕获，按客户端源端口关联 mark 与 NAT 地址；不是用配置权重冒充实际分流。

| 场景 | 独立 HTTP 请求 | wan1 | wan2 | wan3 | wan4 | HTTPS |
| --- | --- | --- | --- | --- | --- | --- |
| 四路在线 | 32/32 返回 204 | 8 | 8 | 8 | 8 | 百度 200，标准证书验证通过 |
| ifdown wan4 后 | 30/30 返回 204 | 10 | 10 | 10 | 0 | 百度 200，标准证书验证通过 |
| ifup wan4 恢复后 | 32/32 返回 204 | 8 | 8 | 8 | 8 | 百度 200，标准证书验证通过 |

- 对应 mark 为 0x100/0x200/0x300/0x400，NAT 地址与相应 vwan 一致。测试数据与脚本见下方本机证据入口。
- wan4 停用后策略只含前三路；恢复后重新进入 25% 均衡。DHCP 将 wan4 地址从 172.21.106.113 改为 **172.21.106.127**；表 104、成员表 4 和 CampusLink 状态全部跟随更新。这同时验证了本次 DHCP 地址变化下的热插拔与路由刷新。
- 最终逐路绑定 vwan 的 HTTP 探测全部返回 204，源 IP 为 .115/.114/.116/.127；CampusLink 四路均在线。源 IP + 设备到校园门户 1.1.1.1 的路由各走对应成员表。
- `fw4 check` 返回 0；SSH 持续可用。Windows WLAN 和路由器本机访问 LuCI 均收到正常登录保护页（HTTP 403，`x-luci-login-required: yes`），证明管理页面可达；本轮没有另建登录会话。设备运行时长持续增长，没有重启或再次刷机。

## 限制与过程修正

- 本次故障测试为 netifd 停用单路接口。未退出真实校园认证会话，因此尚未证明“认证失效但 ICMP 仍可达”时能正确剔除。CampusLink 的联网状态与 mwan3 的 ICMP 状态不是同一个判断；如实际发生这类场景，再增加经过验证的联动。
- 本机直接 UDP DNS 查询超时，TCP 53 连接在 Windows 上返回 WinError 10013，未出现在路由器对应连接记录中。路由器自身解析正常，但客户端 DNS 端到端验证保留缺口；HTTP/TLS 测试使用路由器实际解析出的 IP，不声称该测试覆盖了客户端 DNS。
- 原部署脚本的 nohup 在该固件缺失，后台启动错误未使前台脚本退出。发现后立即改为 setsid，核对真正子进程 PID 与运行状态，最终脚本增加依赖和存活检查。确认标记的无操作分支已执行并核验，未触发回退。
- 自动审批拒绝添加临时 nftables 转发探测链，理由为可能改变防火墙边界；该命令未执行。本次改用保留客户端套接字和只读连接跟踪关联完成分流验证，没有留下测试链/表。
- 吞吐已由后续 [MWAN-03](mwan3-throughput.md)单独实测并记录限制；本次 MWAN-02 不以配置权重推断带宽。未提供单连接带宽合并，未验证全四路同时断开或设备重启；代理/VNT 仍未启用，其未来标记兼容测试不冒充已完成。
