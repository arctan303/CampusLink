# CL-CORE-01：有界并发、账号级熔断与全部检查

来源：2026-10-14 用户确认内部并发上限 2→4，并明确服务器冻结/停用等账号拒绝的熔断“肯定是以账户为单位”。依据 D-20261014-21、[REQ-010 / AC-030–032](../Product-Spec.md)。当前以功能讨论为主，本任务记录已确认边界，不表示已开始代码开发。

范围增量：用户随后选择只增加“全部检查”，不增加“全部登录”，依据 D-20261014-22 / REQ-011 / AC-033–034。复用本任务的调度和认证门禁，有界排队/去重并显示逐路结果；资格有条件过期随后由 D-20261014-23 / [CL-MWAN-07](mwan3-unknown-expiry.md)单独承接，不扩入本任务的运行范围，但须提供可区分账号暂停与网络故障的状态。

目标/范围：在现有调度器/提供商框架中，将 worker 上限提高到 4，保留单路互斥、出口绑定、冷却、取消和旧结果校验；补齐可信账号级拒绝分类及统一账号门禁，停止该账号所有引用线路的自动认证，其他账号保持正常。上线会话不主动退出、不关闭网口；必要状态与账号级恢复交互纳入，不新增并发/熔断调参面板。

非目标：不新增学校协议、任意响应规则或万能关键词匹配，不承诺提速减半/防封号，不实现 TTL、“全部登录”或其他布局优化；不改账号实际值/网络/代理，不推送、公开发布或部署路由器。

依赖与当前证据：daemon 全局上限写死 2，rejected 仅置单路 paused；状态在内存且无关保存/部分绑定变化或重启可能解除。worker 检查后可能进入认证，同账号多个在途 worker 使“收到拒绝后停止其他请求”存在竞争；需要认证前门禁或取消处理。Dr.COM 当前 auth_rejected 还覆盖账号在线/占用等消息，不能不分作用域就全改成账号冻结。新冻结/停用分类需可靠脱敏响应样本，不编造学校返回码。

预期与实施边界：

- 上限 4 仅限制同时执行任务，不限制配置可含超过四路；保证到期任务公平处理，不占满四个槽后长期饿死其他线路。
- 账号级门禁按被引用账号识别；有证据的凭据错误/冻结/停用等才影响全部引用线路，终端/设备限制区分作用域，网络/未知结果沿用退避。没有样本支持的新拒绝保留不确定状态，不通过猜测扩大熔断范围。
- 熔断生效后拒绝同账号新自动认证，在途取消或认证前再次复核；已发请求不能撤回，旧成功结果不自动解锁。原已在线会话可保持，联网检查与认证许可分别处理，mwan3 不因账号暂停而无条件全部退出。
- 修正对应账号凭据或显式账号级恢复解除门禁，受影响线路清晰可见；普通检查/单路绑定变化/无关保存/时段结束/重启/未来批量操作不隐式解锁。恢复仍遵守原服务器冷却。
- 实施时确定账号标识、运行状态/重启恢复、结果作用域表达及恢复入口；不把原始响应或凭据放入状态/日志/报告。与计划停网规则共用认证许可判断，避免双重调度相互解除保护。
- 全部检查覆盖已启用线路，沿用单路 check 和原自动登录开关；账号保护/服务器冷却/停网额度优先。后台排队有界、复用在途任务，不丢弃超出并发上限的线路；重复点击不积累请求。逐路结果区分受理、完成及前提不足/停用跳过，单路失败不终止全批次，配置/绑定变化不执行旧计划或写回旧结果。不调用只读 Doctor 代替普通检查，也不将全部检查宣称为无认证请求。

风险：当前仅产品契约记录。并发改动预计 R1；账号保护的具体实现风险待核验，误分类或错误关联可能使同账号多路停止自动恢复，需可信样本、作用域/恢复/并发竞争验证。若合理检查后仍不能排除全线长时间无法恢复等具体重大影响，按 R2 补相应验证与 fresh reviewer；不以 Markdown 文件或“保护功能”名称降低风险。

验证计划：可控四路/更多线路、请求计数和并发阻塞验证最大 4/单路互斥/公平性/取消/出口隔离；多个账号、同账号多线路、错误/未知/终端拒绝样本验证门禁范围；覆盖同账号在途拒绝与旧成功、服务重启、配置保存、绑定变化、显式恢复和冷却。全部检查覆盖多于四路、重复点击、忙碌/无接口/停用、部分失败、配置变化及认证门禁，验证每路有限批次可完成、反馈不误报联网。复用既有 mock/原生工具，不在真实学校制造封禁或反复认证；发布前按最终影响核验，不把旧 0.3.0 证据当新账号门禁通过。
