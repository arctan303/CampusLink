## 可执行发现

### CL-R01 / P1：取消 worker 没有取消实际 curl 子进程

证据：`daemon.uc:42–44` 只调用 task.kill 后删除工作目录和任务；`transport.uc:22` 用 popen 启动 curl。[ucode task.kill 实现](https://github.com/jow-/ucode/blob/master/lib/uloop.c)只向 worker PID 发送 SIGTERM；[fs.popen 实现](https://github.com/jow-/ucode/blob/master/lib/fs.c)fork/exec 独立子进程，没有父进程死亡信号或对子进程组的终止。

后果：在 curl 已读取含凭据配置、仍在连接或传输时禁用、保存新配置、链路变化或停止服务，只丢弃结果不能撤销请求。curl 仍可能以旧凭据完成登录，且后台已释放该线路锁，可启动新请求。与禁用/配置变化取消任务、单路最多一个在途操作的契约不符。

修复方向：让 worker 与其 HTTP 子进程拥有可整体终止的生命周期，终止确认前保留任务锁；发送前核验当前接口/源地址，清理临时文件。用假凭据、延迟本地 HTTP 端点覆盖禁用、保存、链路变化、服务停止，并观测子进程消失和无后续请求。主会话已计划独立 worker/process group 修复，本轮未验证。

### CL-R02 / P1：启用操作绕过同一接口唯一启用校验

证据：`common.uc:92–93` 只在整份 save 时拒绝启用线路共享接口；`daemon.uc:154–156` 的 enable 直接修改 `c.enabled`，未再验证。两条同接口的禁用配置可以合法保存，随后分别通过 action enable 启用。

后果：两条线路可携带不同账号同时请求同一设备/源 IP；错误账号认证和后续单路退出会影响同一真实出口，违反首版同一逻辑接口至多一条启用配置的有效约束。

修复方向：enable 也应用完整有效配置校验，冲突时返回 interface_in_use，保持内存、磁盘和任务不变。增加“两条禁用同接口配置 → 第一条启用成功 → 第二条启用拒绝”的行为回归。

### CL-R03 / P2：提供商冷却截止时间能被缩短或清空

证据：`daemon.uc:71` 仅在 unauthenticated 结果中保留旧冷却，其他非在线结果在 `74–78` 覆盖 deadline；rate_limited=90 秒后手动检查若返回 indeterminate，新的指数延时可能只有 20 秒。`148` 保存任意配置会重建 states，`155` 禁用/启用会删除状态，也会消除既有冷却。

后果：检查网络故障、修改别名、保存当前配置或启停线路，均可能使自动/手动登录早于服务器要求的最早时间，违反 AC-009 限流遵守冷却和手动操作不能解除冷却。

修复方向：同一受限账号/出口的最早重试时间至少取原 deadline 与新要求的较大者；普通配置和启停不要无条件清空提供商冷却。明确何种身份变化才允许更换冷却作用域，分别验证 indeterminate 检查、无关配置保存、启停后的最早登录时间。

### CL-R04 / P2：未知认证 JSON 被当成必须人工处理的拒绝

证据：`drcom-http.uc:31` 把所有可解析、非成功、非已知密码错误/限流的 JSON 对象统一返回 rejected/auth_rejected；`daemon.uc:73,129` 随后永久 paused。比如 `{"result":10}` 或 `{"msg":"maintenance"}` 均走该路径；现有 provider 测试只检查 parse_response，不验证这段分类。

后果：未知码、服务维护或暂时门户异常停止自动恢复，直到配置或人工重试。provider-v1 明确未知码归 unknown_response，暂时失败由核心退避。

修复方向：仅按有证据的已知拒绝规则暂停；其他未知对象返回 indeterminate/unknown_response，经核验的暂时拒绝继续退避。测试应覆盖完整 login 错误分类和核心后续调度。

### CL-R05 / P2：允许保存的配置超过启动读取上限

证据：`common.uc:4` 最多读 262144 字节，`65–95` 仅限制对象数量和每字段 1024 字符，没有检查序列化总尺寸。使用允许的 64 个账号、32 条线路、128 字符 label、1024 字符用户名/密码和四个 1024 字符 URL，可构造 289880 字节 JSON。本轮用 Node 生成假数据，仅输出尺寸：`account_count=64, connection_count=32, url_bytes=1024, config_json_bytes=289880`。

后果：RPC save 会接受并写入配置，但服务重启后读取被截断，JSON 解析失败、procd 重启循环，全部认证停止。

修复方向：保存前限制整份 UTF-8 JSON 大小并返回 config_too_large，或使读取上限覆盖所有合法配置且明确资源限制。验证边界附近配置保存/重启的往返行为和拒绝后旧配置仍可用。

### CL-R06 / P2：引用账号删除没有约定的提示与引用清单

证据：`main.js:78` 直接把账号从编辑草稿移除；`common.uc:84` 只能在保存时报告 account_in_use_or_missing，RPC 外层包装为 invalid_config，没有列出引用线路。

后果：用户在多路共用账号时点击删除，页面只留下无效引用，保存后才出现机器码错误；不能按 AC-008 与 Architecture 获得“被哪些线路引用”的解释。磁盘配置不会因此损坏，严重度为 P2。

修复方向：删除前显示引用线路并拒绝，后端保留独立引用校验并返回 account_in_use 与 references；验证一个账号多路引用及解除引用后的删除。

### CL-R07 / P2：curl URL globbing 可把一个任务展开成多次认证

证据：`common.uc:47` 允许 URL 路径中的 `{}` 和 `[]`；`transport.uc:8–14` 未设置 globoff。[curl 官方手册](https://curl.se/docs/manpage.html#-g)说明这些字符会展开多个 URL，max-time 的限制针对每个 transfer。即使配置中的 url 已加引号，curl 自身仍会展开 `/login{1,2}`。

后果：一条用户覆盖 URL 能让同一任务多次发送账号请求，越过调度器按任务计数的限频与总耗时假设；目前取消不完整还会放大该问题。

修复方向：固定启用 globoff，或严格拒绝未编码 glob 字符；用本地假凭据接收器证明一个配置 URL 只产生一个请求。主会话传输重构后的选项需要复核。

### CL-R08 / P2：已发布的提供商扩展契约与执行结果不一致

证据：provider-v1 要求 validate 入口、contract_version/operation/reason_code/message、retry_after_s 整数范围和 metadata 语义校验；当前两个 provider 没有 validate，`common.uc:22–25` 无版本/操作字段，`daemon.uc:67` 只校验跨操作的 outcome 集合，provider/school JSON 仅解析和按 ID 装载。logout 的契约结果类别也未包含实现实际使用的 unauthenticated。

后果：贡献者按文档实现的模块与现有模块不遵循同一可执行契约；非法 retry_after_s、错误操作 outcome 或坏 metadata 没有明确拒绝入口，AC-010 的“通过相同契约验证”缺少实现支撑。

修复方向：原位对账一个精简且有效的契约。可复用核心字段校验替代重复 provider.validate，但须在文档明确，并给 metadata、操作结果与扩展样例提供真正的语义验证；不能仅以 JSON 可解析认定通过。不要求增加加密、用户体系或动态插件上传。
